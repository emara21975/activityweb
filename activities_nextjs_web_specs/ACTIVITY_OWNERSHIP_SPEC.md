# المواصفات التنفيذية: نطاق الأنشطة لكل مستخدم

**الحالة:** معتمدة ومنفّذة — 2026-10-16 (نجحت معايير القبول الـ11)
**الهدف:** أن يرى كل حساب الأنشطة التي أنشأها فقط، ويرى المسؤولون جميع الأنشطة.

---

## 1. القرارات المعتمدة

| # | القرار | الاختيار المعتمد |
|---|--------|------------------|
| 1 | طريقة ربط النشاط بالمستخدم | **الأنشطة التي أنشأها فقط** (حقل `created_by_id` الموجود) |
| 2 | الأدوار التي ترى جميع الأنشطة | **مدير النظام، مدير المدرسة، أخصائي الأنشطة** |
| 3 | الأنشطة الحالية (16 نشاطاً كلها باسم `admin`) | **توزيع يدوي من شاشة إدارية** |
| 4 | سجل مشاركات الطالب عند المعلم | **مشاركات الأنشطة المصرح له بها فقط** |

---

## 2. القواعد العامة

- **ق-1:** المستخدم الذي لديه صلاحية `activity.view_all` يرى جميع الأنشطة. غيره يرى فقط الأنشطة التي `created_by_id` = معرّفه.
- **ق-2:** يُطبَّق النطاق **في الخادم** (الخدمات والإجراءات ومسارات API)، وليس بإخفاء العناصر في الواجهة فقط.
- **ق-3:** فتح نشاط خارج نطاق المستخدم (عبر الرابط المباشر) يعرض صفحة «غير موجود» (404) وليس «ممنوع»، حتى لا يُكشف وجود النشاط.
- **ق-4:** أي إجراء على نشاط خارج النطاق (تعديل، أرشفة، تسجيل مشاركات، رفع مرفقات، تصدير) يُرفض برسالة «النشاط غير موجود أو ليس لديك صلاحية عليه».
- **ق-5:** النشاط الجديد يُسجَّل باسم من أنشأه (السلوك الحالي، يبقى كما هو).
- **ق-6:** نقل ملكية نشاط متاح فقط لمن لديه `activity.view_all`، ويُسجَّل في سجل العمليات.
- **ق-7:** حذف مستخدم لا يحذف أنشطته؛ تصبح «بدون مسؤول» (`created_by_id = null`) ولا يراها إلا من لديه `activity.view_all` حتى تُنقل لمستخدم آخر.

---

## 3. الصلاحية الجديدة

| الكود | الوصف | تُمنح افتراضياً لـ |
|-------|-------|--------------------|
| `activity.view_all` | عرض وإدارة جميع أنشطة المدرسة (وليس أنشطته فقط) | `SUPER_ADMIN`، `SCHOOL_ADMIN`، `ACTIVITY_SUPERVISOR` |

- تُضاف إلى `lib/auth/permissions.ts` و`prisma/seed.ts`.
- قابلة للتعديل لاحقاً من صفحة «الأدوار والصلاحيات».
- **ملاحظة:** «قارئ التقارير» لا يحصل عليها افتراضياً حسب القرار 2، أي سيرى أنشطته فقط (وهي غالباً صفر). يمكن منحه إياها من مصفوفة الصلاحيات إذا لزم.

## 4. التصميم التقني

### 4.1 دالة نطاق موحّدة — ملف جديد `lib/auth/activity-scope.ts`

```ts
// يعيد شرط Prisma يُدمج في أي استعلام على الأنشطة
getActivityScope(user): Prisma.ActivityWhereInput
//   view_all  → {}
//   غير ذلك   → { created_by_id: user.id }

// يعيد شرطاً للمشاركات (عبر النشاط)
getParticipationScope(user): Prisma.ParticipationWhereInput
//   view_all  → {}
//   غير ذلك   → { activity: { created_by_id: user.id } }

// يتحقق من نشاط واحد ويرمي خطأ إذا كان خارج النطاق
assertActivityInScope(user, activityId): Promise<void>
```

### 4.2 قاعدة البيانات
- **لا تغيير في الجداول.** الحقل `created_by_id` موجود ومفهرس عبر العلاقة.
- **لا حاجة لفهرس إضافي:** MySQL (InnoDB) يُنشئ فهرساً تلقائياً لكل مفتاح أجنبي، ومنها `created_by_id`.

## 5. المواضع التي يجب تطبيق النطاق عليها

### أ) الأنشطة
| الموضع | الملف | التغيير |
|--------|-------|---------|
| قائمة الأنشطة | `lib/services/activity-service.ts` → `getActivities` | إضافة خيار `scope` يُدمج في `where` |
| تفاصيل النشاط | `app/(dashboard)/activities/[id]/page.tsx` | `notFound()` إذا خارج النطاق |
| تعديل / تعديل سريع / تغيير الحالة / أرشفة / رابط الفيديو | `app/actions/activity-actions.ts` | `assertActivityInScope` قبل التنفيذ |
| حفظ بيانات التقرير | `app/actions/activity-report-actions.ts` | `assertActivityInScope` (حالياً بدون أي فحص صلاحية — يُصلح) |
| تصدير الوورد | `app/api/activities/[id]/export/word/route.ts` | 404 إذا خارج النطاق |

### ب) المشاركات
| الموضع | الملف | التغيير |
|--------|-------|---------|
| صفحة تسجيل المشاركات (قائمة الأنشطة المنسدلة) | `app/(dashboard)/participations/page.tsx` | تمرير النطاق إلى `getActivities` |
| تسجيل مشاركات | `app/actions/participation-actions.ts` | `assertActivityInScope` على النشاط |
| إلغاء مشاركة | `app/actions/participation-actions.ts` | التحقق من نطاق نشاط المشاركة |

### ج) المرفقات
| الموضع | الملف | التغيير |
|--------|-------|---------|
| رفع مرفق | `app/actions/attachment-actions.ts` | `assertActivityInScope` |
| حذف/أرشفة مرفق | `app/actions/attachment-actions.ts` | `assertActivityInScope` |
| تحميل/عرض مرفق | `app/api/attachments/[id]/route.ts` | 404 إذا كان نشاط المرفق خارج النطاق |

### د) الطلاب (القرار 4)
| الموضع | الملف | التغيير |
|--------|-------|---------|
| ملف الطالب — سجل المشاركات | `lib/services/student-service.ts` → `getStudentById` + صفحة الطالب | تُعرض فقط المشاركات في أنشطة ضمن النطاق، والعدّاد يعكس ذلك |
| قائمة الطلاب | بدون تغيير | بيانات الطلاب الأساسية تبقى ظاهرة (المعلم يحتاجها لتسجيل المشاركات) |

### هـ) لوحة التحكم والإحصائيات والتقارير
| الموضع | الملف | التغيير |
|--------|-------|---------|
| لوحة التحكم | `lib/services/statistics-service.ts` → `getDetailedDashboardData` / `getDashboardMetrics` | دمج النطاق في `activityWhere` واستعلامات المشاركات؛ المعلم يرى أرقام أنشطته فقط |
| صفحة الإحصائيات | `app/(dashboard)/statistics/page.tsx` | نفس النطاق |
| تقرير الأنشطة `act` | `app/(dashboard)/reports/[type]/page.tsx` | نطاق المستخدم |
| التقرير الإحصائي الرسمي `stat` | نفس الملف + `report-service.ts` | **يتطلب `activity.view_all`** (تقرير على مستوى المدرسة) |
| تقرير غير المشاركين `non-participants` | نفس الملف + `report-service.ts` | **يتطلب `activity.view_all`** (لا معنى له على مستوى نشاط معلم واحد) |
| تصدير Excel | `app/api/reports/export/excel/route.ts` | نطاق المستخدم، والتقارير المدرسية تتطلب `view_all` |
| قائمة التقارير | `components/reports/ReportsNav.tsx` | إخفاء التقارير المدرسية عمّن لا يملك `view_all` |

### و) خارج النطاق (بدون تغيير)
- النسخ الاحتياطي، تفريغ البيانات، الاستيراد: إجراءات إدارية محمية بصلاحياتها الحالية وتعمل على كامل البيانات.

## 6. شاشة توزيع الأنشطة (القرار 3)

**المكان:** صفحة جديدة `/activities/assign` (رابط من صفحة الأنشطة، يظهر فقط لمن لديه `activity.view_all`).

**المحتوى:**
- جدول بكل الأنشطة: اسم النشاط، التاريخ، التصنيف، **المسؤول الحالي** (قائمة منسدلة بالمستخدمين النشطين).
- فلتر: «بدون مسؤول»، «باسم admin»، حسب التصنيف، بحث بالاسم.
- **تحديد متعدد + «إسناد المحدد إلى…»** لتوزيع عدة أنشطة دفعة واحدة.
- زر حفظ لكل صف، أو حفظ جماعي.

**أيضاً:** في صفحة تفاصيل النشاط، يظهر لمن لديه `view_all` حقل «المسؤول عن النشاط» قابل للتغيير.

**الخدمة:** `reassignActivities(activityIds[], newOwnerId, actorId)` في `activity-service.ts`
- تتحقق أن المستخدم الجديد موجود ونشط.
- تُحدّث `created_by_id` و`updated_by_id`.
- تسجّل في سجل العمليات: `REASSIGN_OWNER` مع المالك السابق والجديد لكل نشاط.

## 7. معايير القبول (الاختبار)

| # | السيناريو | النتيجة المتوقعة |
|---|-----------|------------------|
| 1 | معلم يفتح صفحة الأنشطة | يرى أنشطته فقط |
| 2 | معلم يفتح رابط نشاط لمعلم آخر | صفحة 404 |
| 3 | معلم يحاول تصدير وورد / تحميل مرفق لنشاط غيره بالرابط | 404 |
| 4 | معلم يسجّل مشاركات في نشاط غيره (طلب مباشر) | مرفوض |
| 5 | معلم ينشئ نشاطاً جديداً | يظهر في قائمته فوراً |
| 6 | أخصائي الأنشطة / مدير المدرسة / مدير النظام | يرون جميع الأنشطة كما الآن |
| 7 | معلم يفتح ملف طالب | يرى مشاركات الطالب في أنشطته فقط، والعدد مطابق |
| 8 | معلم يفتح لوحة التحكم | الأرقام تخص أنشطته فقط |
| 9 | معلم يفتح التقرير الإحصائي أو غير المشاركين | غير متاح |
| 10 | المدير يوزّع 16 نشاطاً من شاشة التوزيع | تظهر لدى المعلمين المعنيين، ويُسجَّل النقل في سجل العمليات |
| 11 | حذف معلم لديه أنشطة | الأنشطة تبقى وتظهر «بدون مسؤول» في شاشة التوزيع |

## 8. خطة التنفيذ

| المرحلة | المحتوى | التقدير |
|---------|---------|---------|
| 1 | الصلاحية الجديدة + دالة النطاق + فهرس قاعدة البيانات | 1 ساعة |
| 2 | الأنشطة والمشاركات والمرفقات والتصدير (أ، ب، ج) | 2–3 ساعات |
| 3 | الطلاب ولوحة التحكم والإحصائيات والتقارير (د، هـ) | 2–3 ساعات |
| 4 | شاشة التوزيع + حقل المسؤول في صفحة النشاط | 2 ساعة |
| 5 | الاختبار حسب معايير القبول + الرفع على main | 1 ساعة |

**إجمالي تقديري:** يوم عمل واحد.

**على خادم الإنتاج بعد الرفع:** إضافة صلاحية `activity.view_all` ومنحها للأدوار الثلاثة، ثم توزيع الأنشطة الحالية من شاشة التوزيع **قبل** إبلاغ المعلمين (وإلا سيجدون قوائمهم فارغة).
